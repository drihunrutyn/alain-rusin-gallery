# Alain Rusin — персональная галерея

Полная серверная версия на утверждённом стеке Runable: Bun, Vite, React, Hono, TypeScript strict, Drizzle. Публичные страницы и закрытый кабинет работают с одной внешней базой Turso (SQLite) и внешним Tigris S3-хранилищем. Next.js и Supabase в этой реализации не используются.

## Работающее развёртывание
- Сайт: https://alain-rusin.alainrusin.deno.net
- Вход в кабинет: https://alain-rusin.alainrusin.deno.net/admin/login
- Приватный исходный код: https://github.com/drihunrutyn/alain-rusin-gallery
- Deno Deploy: приложение `alain-rusin`, ветка `deno-deploy`. Render ниже оставлен как резерв, без отключения и удаления данных.
- Render: Docker Web Service `alain-rusin`, Free ($0/month), Oregon, ветка `main`; полная серверная версия, не static site. GitHub App получила доступ только к этому новому репозиторию, остальные выбранные репозитории сохранены.
- Проверено 29 октября 2026: Render сообщил Live, health 200, страницы/SEO/404, анонимный доступ запрещён, вход/выход, CRUD работ и контента, заявки, подписка, аналитика, загрузка в Tigris и публичное чтение, фильтры, примерка, мобильная вёрстка, PDF (6 страниц A4, кириллица). Браузерных ошибок нет. Тестовые записи и объект удалены; тестовые просмотры остались в аналитике. Фактическая смена пароля не выполнялась, проверен отказ при неверном текущем пароле.

## Возможности
- Каталог: фильтры по серии, технике и статусу, отдельные страницы работ.
- Заявки и подписчики сохраняются в базе; необязательные Telegram-уведомления.
- Кабинет: CRUD работ, загрузка фотографий, featured, заявки и статусы, интервью/статьи/пресса/выставки, настройки и смена пароля, комнаты.
- Дашборд: реальные просмотры, заявки, SVG-графики, топ-5 работ.
- PDF на клиенте: только доступные работы, группировка по сериям, локальные кириллические TTF, контакты и QR.
- Примерка: три CSS-сцены, свои фото интерьеров, перетаскивание мышью/тачем/стрелками и масштаб.
- Серверная выдача SEO-метаданных, canonical, OG, Person и VisualArtwork JSON-LD; sitemap.xml, robots.txt, корректный 404.

## Локальная разработка
1. Bun 1.3.14 или совместимая более новая версия.
2. `bun install --frozen-lockfile`.
3. Создать единственную корневую `.env` по `.env.example`. Не коммитить реальные значения.
4. `bun run --cwd packages/web db:push`.
5. Для новой базы один раз: `bun --env-file=.env packages/web/scripts/seed.ts`. Скрипт не перезаписывает записи с существующими id.
6. `bun run dev` — единый frontend и API на назначенном порту 4200 из `.runable/ports.json`.
7. `bun run --cwd packages/web build`, `bun run lint`.

Файлы и папки с `__` — управляемая инфраструктура, их нельзя менять. Обязательная аналитика Runable сохранена.

## Deno Deploy из приватного GitHub
1. Push в `deno-deploy` запускает `.github/workflows/deno-deploy.yml`.
2. GitHub Actions собирает frontend и SSR-сервер на Node 24: `npm ci`, `npm run build`. Это обходит несовместимость jsdom/@exodus/bytes со сборкой Vite внутри Deno.
3. `build-deno.mjs --seal` создаёт SHA-256-манифест. В Deno отправляются исходники, `dist` и `dist-edge`; `.env` и зависимости из локального `node_modules` не отправляются.
4. Deno выполняет `npm ci` и `npm run build`: уже собранные файлы проверяются по манифесту, Vite повторно не запускается. Entry point — `packages/web/dist-edge/server.js`.
5. GitHub secret: `DENO_DEPLOY_TOKEN`; variables: `DENO_APP_ID`, `DENO_DATABASE_INSTANCE`. Секреты приложения остаются в Deno, Turso и Tigris не заменяются.
6. В production `Deno.openKv()` использует подключённую управляемую базу для сессий, ограничений частоты и метрик. `:memory:` допустим только при локальной разработке. Не задавать `DENO_KV_URL=:memory:` в production.
7. Workflow читает поток прогресса до конечного статуса. Ошибка сборки завершает workflow с ошибкой; прежняя успешная ревизия остаётся рабочей. После успеха проверяются health и sitemap.
8. Telegram остаётся выключенным до настройки `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`.

## Render Free из приватного GitHub (резерв)
1. Новый приватный репозиторий, исключены `.env`, токены, пароли, QA, локальные базы, логи. **`.runable/ports.json` нужно сохранить в Git**: его читает `__ports.cjs` при сборке.
2. Render → New Web Service → Git Provider → нужный репозиторий, Docker, ветка main, корень. Выбрать **Free ($0/month)**, не платный тариф.
3. Перенести только переменные, которые использует сайт: `DATABASE_URL`, `DATABASE_AUTH_TOKEN`, `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `ADMIN_LOGIN`, `ADMIN_PASSWORD`, `AUTH_SECRET`, `APPLICATION_ID`, `WEBSITE_URL`. Последняя — фактический HTTPS-адрес сервиса. Секрет сессии — случайный минимум 32 символа.
4. При необходимости установить `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`. Без них заявки сохраняются, но Telegram не отправляется. Статус виден в настройках.
5. Docker собирает `packages/web`, запускает `packages/web/src/server.ts`, который читает Render `PORT` и отдаёт dist и API. Это расширенный production-entrypoint с SEO и защитой административных страниц; шаблонный `__server.ts` не изменён.
6. Уже настроенная внешняя база и S3 используются напрямую: не создавать локальную SQLite и не запускать очистку или повторную инициализацию при старте контейнера. Изображения грузятся через временные presigned URL в Tigris, а не на диск Render.
7. После Deploy succeeded проверить `/`, `/api/health`, каталог, изображения/шрифты, `/api/auth/me` без сессии (401), вход в кабинет, CRUD и PDF. Запрос `/admin` без сессии перенаправляется в `/admin/login` (302), приватные oRPC возвращают 401.

Render Free засыпает после 15 минут простоя; холодный запуск может занять минуту и более. Публичная доступность из конкретной сети и без VPN проверяется владельцем. Платных ресурсов проект не требует, но квоты внешних провайдеров нужно контролировать в их интерфейсах.

## Авторизация и API
`POST /api/auth/login`, `GET /api/auth/me`, `POST /api/auth/logout` — HTTP-only SameSite=Lax cookie, 7 дней, jose HS256. Логин/исходный пароль только в окружении; смена пароля хранит Argon2id-хеш в admin_settings, отзывает все старые сессии. Публичной регистрации нет. Ограничение частоты входа и публичных записей; Zod-валидация, проверка ссылок и источника приватных запросов.

По правилам утверждённого стека бизнес-API реализовано типизированными oRPC, **не Next.js API routes**:
- `/api/rpc/gallery/artworks`, `artwork`, `content`, `profile`, `rooms`, `request`, `subscribe`, `view`, `me`.
- `/api/rpc/management/artworks`, `saveArtwork`, `deleteArtwork`, `content`, `saveContent`, `deleteContent`, `requests`, `processRequest`, `stats`, `settings`, `saveSettings`, `password`, `upload`, `saveRoom`, `deleteRoom`, `subscribers` — серверная проверка сессии для каждой операции.
- `/api/health` — здоровье процесса.

Публичные клиенты не имеют доступа к заявкам, подписчикам, хешам или ключам хранилища. Настройки PDF возвращают только email и город. Секреты не имеют VITE-префикса и не попадают в браузерный bundle.

## Важные редакционные ограничения
Сид-метаданные и цены взяты дословно из ТЗ. Вложения содержат только морской этюд, триптих, логотип и баннер Артхива, **не четыре отдельные фотографии указанных в ТЗ оригиналов**. Остальные изображения — фрагменты предоставленного триптиха, предварительные иллюстрации серий. Не утверждается, что это фотографии работ с такими названиями и характеристиками. Для продаж нужно загрузить подтверждённые оригинальные фото через кабинет. Картины не генерировались.

Полный юридический текст политики не был предоставлен в копи-деке. `/privacy` содержит предоставленную формулировку согласия и прямо указывает необходимость текста от владельца. Это не юридически проверенная политика; до публичного сбора персональных данных владелец должен предоставить и утвердить её.

Telegram не настроен без необязательных секретов. Премии, номинации и членство отображаются как предоставленные владельцем сведения, без независимой проверки.

## Netlify / Supabase
Статический перенос на Netlify **не сохраняет серверную версию**. Для полного переноса требуется адаптер Netlify Functions и замена Bun-specific password API; обещать перенос без изменения кода нельзя. Существующие React-страницы и внешние данные можно сохранить, но серверный runtime отличается.

`supabase/schema.sql` — дополнительная схема исходного ТЗ для возможной будущей миграции, не активная база этого сайта. Выполнение её не переводит действующее приложение на Supabase: для этого нужны отдельный адаптер данных, storage/auth environment и согласованная миграция без потери записей.
